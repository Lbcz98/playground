Design for a Chrome 68 TV

Real viewers watch on TV browsers about as old as Chrome 68, on a weak chip, with a remote. This guide says what that engine can and cannot draw, which effects make it stutter, and how to design around both.

How to read this guide

Every claim carries one label. We never upgrade a label.

About the demos. They run in your browser, which is much newer and faster than the TV. They show the rule. They cannot reproduce TV timings. The timings on this page come from the TV.

The ten rules in one screen

  1. Animate only transform and opacity, and give them pixel values.Same animation: 181 style passes with a percent translate, 0 with pixels.
  2. Never put a percent translate inside keyframes.Centre with margins, anchors, or calc() that resolves to pixels.
  3. Centre with margin: auto as well as place-items.Chrome 68 drew a round button circle 8 px left of centre. The root cause is not known.
  4. Give every linear() spring a cubic-bezier fallback.linear() starts in Chrome 113.
  5. Do not use color-mix, relative colour, :has(), :focus-visible, inset, logical properties or flex gap without a fallback.Use the project fallbacks.
  6. Run few infinite animations at once.A trace of the idle home shows four loops running. Their exact cost was not isolated.
  7. Keep the same element in the same place in the React tree between states.Otherwise about 130 elements are thrown away and rebuilt on every key.
  8. Never render a <style> inside JSX.The fix was applied on reasoning. Its own effect was not separated from noise.
  9. Judge feel on a production build, never on the dev server.First screen 11 s in dev, 3 to 5 s in production.
  10. Run one browser at a time on the TV.A background WebView of about 180 MB led to low-memory kills and a renderer crash.

TV mode: 1280×720 and fullscreen

Add ?tv=1 to the URL. The viewport meta tag becomes width=1280, so the stage draws at 1280×720 and scale 1.

  • Before fullscreen, Chrome 68 reports 1280×668. The URL bar takes 52 px.
  • On the first key press the page asks for fullscreen (the prefixed webkit API in Chrome 68).
  • In fullscreen, ContentShell forces the layout to 960 wide. The stage then draws at scale 0.75. The pixels on screen are the same. It is not a 1280 layout.

The harness: tvperf.mjs

A Node script drives the page over the DevTools protocol and reports, for every key press:

  • milliseconds until the new flow state is in the DOM;
  • frames drawn in the next 1.2 s (about 72 means smooth at 60 fps);
  • the longest gap between frames;
  • long tasks (main-thread blocks over 50 ms).

--trace records a Chrome trace. traceinfo.mjs reads it and splits main-thread time per key into script, style, layout, paint, commit and GC, and names the biggest style pass and its element count. --css injects rules to A/B a suspect. --adb sends real remote keys.

Lessons about the rig itself

  • Run each variant at least twice. Two identical WebView runs gave 22 and 43 janky frames. Baseline-to-baseline noise was as large as many effects we tried to see.
  • Reading innerText inside a probe forces layout and fakes stalls. An early report of "1 to 4 s on first visits" was this artefact. Real screen changes appear 40 to 170 ms after the key.
  • Keys sent over DevTools do not count as user activity for Android. The harness sends KEYCODE_WAKEUP every minute.
  • Hanging DevTools calls need timeouts. Two runs in our notes timed out after 360 s.

What Chrome 68 does not support

Each missing feature has a fallback in the project. All fallbacks are additive, so modern browsers render exactly as before. A few things have no fallback and simply cannot be done.

First problem: the page did not start

Next 16 builds for Chrome 111 by default. In that build, 56 of 83 JavaScript chunks did not parse in Chrome 68. The page stayed white on "Carregando tela…".

npm run build:tv sets BROWSERSLIST="chrome >= 68, safari >= 16" and writes to .next-tv. All 85 chunks then parse as ES2019.

What cannot be done

The colour-cycling focus ring. It needs relative colour, oklch(from …), which starts in Chrome 119. In Chrome 68 the keyframes erased the ring, so the cycle is off and a static ring shows. This also changes Chrome 111 to 118 and Safari 16.4 to 17. Design a static ring first. Treat the cycle as a bonus for new browsers.

:has() has no full fallback. Two cases stay degraded: a resting card whose footer holds a WideButton stays dimmed, and a <Link> around a kit surface keeps the browser's own outline.

Demo: flex gap and its fallback

Chrome 68 ignores gap on flex containers. The early script puts no-flexgap on the html element. Children then get margins per direction and step. The margins spring like gap did.

A centring bug without a known cause

place-items: center did not centre the kit's round-button circle horizontally in Chrome 68. The circle sat 8 px left of the button centre. The ripple and the tooltip are anchored to the true centre, so they looked shifted. Adding margin: auto on .sfs-round-button-circle fixed it.

Root cause unknown. The button's grid track reported none in Chrome 68 and 88px in modern Chrome. Rule for designers: never trust place-items alone for a single grid child. Add margin: auto.

.sfs-round-button-circle {
  place-items: center;
  margin: auto; /* Chrome 68 needs this */
}

Beyond CSS: keys, Back, memory, video

Several problems on the TV had nothing to do with styling. They still change what a designer can promise.

Arrow keys and focus

Chrome 68 has no spatial navigation. Arrow keys only scroll the page, so link lists were unreachable.

TV mode now moves focus to the nearest link or control in the arrow's direction. Flows read the keys themselves and are left alone. Design implication: any new list of links works with the arrows. A custom widget must handle its own keys.

The Back button

The remote's Back becomes history.back() on Android. It left the flow.

TV mode keeps one history entry in front of the flow. Each Back pops it and is turned into the flow's Back. At the hidden state, or when Back changes nothing, the next Back leaves. Design implication: tell developers what Back does on every screen.

Fullscreen and viewport

The first key press asks for fullscreen. In fullscreen ContentShell lays the page out at 960 wide and the stage draws at scale 0.75. We have not checked whether real Chrome 68 TV browsers do the same. Do not design around a 960 layout. Design for the 1280×720 stage.

The clock

The TV clock is UTC. "On now" programme logic gives different answers than on the Mac. The TV's time zone is set in Settings, Device Preferences, Date and time.

Video

  • This open-source Chromium 68 build has no H.264 or AAC. MediaSource.isTypeSupported is false for H.264 and true for VP9 in WebM. It has no native HLS.
  • hls.js 1.5.17 starts on Chrome 68 (isSupported true, playlist and first segment fetched) but never plays. The Globo stream cannot play in the test build. The modern WebView plays it.
  • Real Chrome 68 TVs have H.264. Broadcast video on a real TV is drawn on a separate hardware plane. So an empty background does not make our test lighter than reality. The screens look emptier.
  • Option: use a VP9/WebM background clip in the test build.
  • The Android WebView shows a grey play-icon poster before the first frame. The app fixes it with getDefaultVideoPoster.
  • The Globo stream URL has an expiring token. An expired one returns HTTP 403.

Network setup

  • Next's dev server blocks hot reload from non-localhost origins. The page hung on "Carregando tela…". The fix is allowedDevOrigins: ['192.168.*.*'] in next.config.mjs.
  • The TV's IP and the Mac's IP changed several times. Reserve both in the router.

Motion and animation rules

The most important page. One rule alone, no percent translates in keyframes, removed a restyle of the whole page on every frame.

Percent versus pixel translate

An animation can run on the compositor (the graphics side, off the busy main thread) or on the main thread. On the main thread the page is restyled every frame.

In Chrome 68, a CSS animation with a percent translate in its keyframes (translateX(-160%), translate3d(-50%,-50%,0)) is not run on the compositor. The page restyled about 180 times in 3 s and spent about 70 ms of main-thread style time while it ran.

The same animation with pixel values, or with calc(var(--x) * 1.6) that resolves to pixels, showed 0 style passes. Isolated test pages: percent 181, px 0, calc-px 1.

Looks identical in modern browsers
Percent keyframes. TV: 181 style passes
Pixel keyframes. TV: 0 style passes

Both lanes move the same here. The difference exists only in how Chrome 68 schedules the work. Your browser cannot show that.

Style passes in 3 s, isolated page on the TV
/* Wrong in Chrome 68: restyles the page every frame */
@keyframes sweep { from { transform: translateX(-160%) } to { transform: translateX(160%) } }

/* Right: resolves to pixels, stays on the compositor */
.band { --o11-band-px: 120px; }
@keyframes sweep { from { transform: translateX(calc(var(--o11-band-px) * -1.6)) }
                   to   { transform: translateX(calc(var(--o11-band-px) *  1.6)) } }

Fixes applied: the profile-button light sweep in MenuComPerfilAnimado.tsx uses --o11-band-px. The kit's badge halo (sfs-alert-bug-in-halo, -out-halo, .sfs-alert-bug-halo) uses calc(var(--_alert-bug-halo) / -2).

Not fixed, not measured. MenuComTooltip.tsx keyframes mpt-crescer, mpt-encolher, mpt-dot-sobe, mpt-esticar, mpt-comprimir and mpt-assentar use translate(-50%, -50%) in percent. The tooltip morph very likely runs on the main thread in Chrome 68. This is the next thing to test.

What stayed on the compositor in Chrome 68

All of these were fine, with 0 extra style passes in the isolated test:

  • custom properties inside keyframes (var(--x) in scale and opacity);
  • cubic-bezier timing and fill-mode: both;
  • filter: blur(12px) on the animated band;
  • clip-path: circle(), and overflow: hidden with border-radius;
  • will-change: transform, opacity;
  • multi-stop keyframes with opacity.

What can never be on the compositor

In any Chromium, animating width, height, padding, border-radius, filter or background-image runs on the main thread. We did not isolate this on the TV.

A decision to keep, knowingly. The kit's one 800 ms spring is applied on purpose to width, height and padding on focus expansion. That is the project motion law. So it will always cost main-thread style and layout in Chrome 68. Do not try to "fix" it. Just do not stack more main-thread work on top at the same moment.

Infinite animations

A trace of the idle home screen shows these running forever:

  • the profile effect: two o11-wave scale and opacity loops and the o11-sweep band, an 8.5 s cycle;
  • the focus ring background-image colour cycle and the focus glow cycle. On modern engines both run on the main thread, because they animate a background image;
  • the AlertBug halo spin.

In Chrome 68 the ring cycle is off (see the fallbacks). We call these the biggest standing load. That is a reading of the trace. We did not turn them off one by one and measure.

Design rule: count the loops on a screen. Keep that count small, and prefer loops that animate only transform and opacity in pixels.

Cost of effects, measured

Some ideas are slow in a test page but make no difference on the real page. This page keeps both facts side by side, so nobody spends time on the wrong fix.

Pick a measurement

…

Numbers come from the TV in Chrome 68. The chart only draws them.

Each transitioned property costs style time

Isolated page, 70 boxes with 2 children each, a class toggled. Median style time per pass: no transition 7.9 ms, one property 19.5 ms, the kit's 14-property list 49.8 ms. The 14 properties are width, height, min-width, min-height, padding, gap, background-color, border-color, border-radius, color, opacity, box-shadow, transform and outline-color, on .sfs-motion, .sfs-motion *.

On the real page, cutting the descendant list to 4 properties changed little: janky frames went from 18 to 15 over 7 keys, within noise. Treat this as a cost to avoid adding to. It is not a proven big win.

Tokens (var()) cost about 3 times a literal

Isolated: 104 elements × 25 declarations took 34 ms with var(--token) and 10 to 12 ms with literals. The 288 root custom properties alone, and inline custom properties, had no effect.

But a PostCSS step that replaced constant tokens with literals (it removed about 75% of var() in the kit CSS) did not improve the real page. Jank was 22 and 29 against 18 to 20 for the baseline. We dropped it. Do not spend effort removing tokens.

Things that changed nothing

  • Own compositor layers (will-change: transform on cards and buttons): same frames, same long tasks, same memory. Janky frames: 15 and 20 with layers, 19 without (one other no-layer run returned no data). Page process memory stayed near 127 MB.
  • In the modern WebView, switching off mix-blend-mode: luminosity, filter, masks and clip-path, video, transitions or animations, one at a time, gave no clear win over baseline noise. Do not blame blend modes or blur without a trace.
  • A whole-screen transform: scale() on the stage and full-screen gradients over video exist in the design. We have no isolated measurement. TV mode keeps the stage at scale 1.

Demo: what a long block does to frames

At 60 fps a frame lasts about 16.7 ms. A main-thread block of that length or more drops frames. The harness looks at 1.2 s after each key, which is about 72 frames when nothing blocks.

Element by element

What each kit element draws, how it behaves in Chrome 68, and how risky it is. "Risk" is our reading of the evidence, not a score from the TV.

The table

React structure on a slow CPU

On this TV, how the screen is built in React matters as much as the CSS. Three changes removed most of the stalls on menu moves.

The menu was rebuilt on every key

A trace with invalidation tracking showed it. Moving focus between home-program and home-misc threw away and rebuilt the whole menu: about 130 elements added and removed per key. Its spring popped instead of animating.

Cause: the two screens put the menu at different places in the React tree. React saw a different element and replaced it.

Fix: all five home states share one wrapper Stack and key="menu". Design rule: if an element lives across two states, place it at the same spot in both. Then it updates, and the spring runs.

A style element in JSX

A <style> element inside JSX was re-inserted on every focus change. The page re-reads the sheet and restyles everything. It is now installed once per page (estiloUnico.ts).

We applied this on reasoning and on a trace of repeated style recalculations. Its isolated effect was not separated from noise in the A/B. Call it plausible.

One render per state change

The flow player went through a "loading" render, with a status label in and out of the page, on every key, even for states already loaded. It now switches in one render. The effect was not isolated.

Before and after, per key

Chrome 68, flow bug-home-login, keys 400 ms apart. Before the fixes, every key showed a 50 to 110 ms main-thread block. After: menu moves show none (63 to 72 of about 72 frames). Only mounting a new screen costs 50 to 90 ms. Entering the home costs 85 to 90 ms. The first time in the rail costs about 60 to 75 ms. The longest frame gap was 37 to 134 ms, and the worst, 134 ms, is the first key.

The noise we had to live with

An earlier baseline pair, same build: key "left home-bug to home-program" gave 32 frames and a 149 ms long task in one run, 24 frames and 212 ms in the next. That is why single A/B runs on this page are labelled noisy.

How to measure

Run the Chrome 68 copy, drive it with the harness, and read frames, gaps and long tasks. Never judge from one run.

A test protocol

  1. Use a production build.
  2. Close every other browser on the TV. Run one engine.
  3. Run the same keys at least twice per variant.
  4. If two identical runs differ as much as your variants, the result is noise. Say so.
  5. Do not read innerText or other layout-forcing properties in a probe.
  6. For a suspect, trace it and look at style passes per key, not just frames.
  7. Keep the Mac and TV IPs reserved in the router.

Reading a trace

traceinfo.mjs prints per key the main-thread self time by category (script, style, layout, paint, commit, GC) and the biggest style pass with its element count. A high style number with a high element count points to a restyle that touched much of the page, such as a percent-translate loop or a rebuilt subtree.
