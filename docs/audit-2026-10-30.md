**1. P1 — Applying values to one tuned option overwrites another option's styles. Reproduced.**

Source: [scripts/explore-tune.mjs:74](/Users/lucas/playground/scripts/explore-tune.mjs:74).

`applyTuned` finds the requested option's JSON spec, but replaces the first `tune:vars` CSS block anywhere in the document. With two tuned options, updating option 2 destroys option 1's block and leaves option 2's old block later in the document. That later block can override the newly written values, so the spec and visible result disagree.

Probe: option 1 started with `--width: 10px`, option 2 with `20px`. Applying `30px` to option 2 produced two CSS blocks for option 2, at `30px` and `20px`, and no block for option 1. The operation returned `changed: 1`.

Fix: identify CSS blocks by option ID and require exactly one matching block before writing. Apply the same scoping to `lintSpec`, which also reads the first global block. Add a regression with multiple tuned options and assert that every non-target option remains byte-for-byte unchanged.

**2. P1 — Multiple focused instances of a local component are counted only once. Reproduced through the full render gate.**

Source: [scripts/check-laws.ts:322](/Users/lucas/playground/scripts/check-laws.ts:322).

The focus walker uses one shared `seen` set keyed by the component's declaration node. This prevents recursion, but also skips a second independent instance of that component. If the component internally sets `interactionState="focus"`, two instances render two focus holders while the checker counts one.

Probe: took the existing `local-component-holds-focus` corpus fixture and changed `<Pick />` to `<Pick /><Pick />`. `runChecks(..., { requireRender: true })` returned exit code 0, no findings, no problems, no warnings, and zero unread constructs.

Fix: use an ancestry/recursion guard that is removed when leaving a component, while counting each JSX instance. Also apply the existing DOM focus-reading logic to standalone screen checks, so the render gate independently verifies `focus.single`. Cover repeated instances, nested wrappers, and conditional/repeated content.

**3. P1 — CI and deployment discard changes that can invalidate existing screens. Reproduced at the selector boundary.**

Sources: [scripts/protos-ci.ts:22](/Users/lucas/playground/scripts/protos-ci.ts:22), [scripts/deploy.ts:150](/Users/lucas/playground/scripts/deploy.ts:150), [src/shared/protoFolders.ts:88](/Users/lucas/playground/src/shared/protoFolders.ts:88).

`screensOf` and deployment's `classify(...).screens` keep only `.tsx` and `flow.ts`. A change to a normal `.ts` data/helper file is discarded before `checkTargets` can expand it to affected screens. JSON changes are also excluded. A data-only change can therefore add overflowing rows or alter screen content without running its screen laws/render audit. Flow probes may still run for a touched designer, but do not replace the omitted screen checks.

Probe: both CI and deployment returned `[]` for `web/protos/ana/data.ts`, while handing that same path directly to `checkTargets` selected `home.tsx` in a representative folder tree. A shared kit-file change also produced no prototype check targets; shared kit/token changes currently rely on the fixed test corpus and web build rather than checking every existing prototype.

Fix: preserve all relevant changed paths until a single impact-selection function expands them. Recheck a designer's screens for local data/helper changes, and all prototypes for shared kit/token/rule changes. Include JSON inputs. Test the complete CI/deployment input path, rather than only the downstream folder helper.

**4. P1 — Installed dependencies have known security advisories. Version findings confirmed; exploitability depends on usage.**

Sources: [package.json:41](/Users/lucas/playground/package.json:41), [web/package.json:13](/Users/lucas/playground/web/package.json:13), [design-brain/package.json](/Users/lucas/playground/design-brain/package.json).

- Installed Storybook `10.6.0` is affected by a critical preview-origin/code-injection advisory, [GHSA-f2ph-cmg5-wxc8](https://github.com/advisories/GHSA-f2ph-cmg5-wxc8), and a local-network dev-server advisory. The reported affected range ends before `10.6.2`. This matters because running Storybook and its MCP addon is a documented normal workflow.
- Next.js is pinned to `14.2.35`; npm reports critical advisories and recommends a major upgrade. Several advisories require specific features or hosting configurations. This audit does not establish that those exploit paths are reachable in this viewer.
- Vitest `2.1.9` and its dependency tree carry advisories, including an exposed UI-server issue. `vitest run` passing does not establish exposure to that server issue. Vite, Zod, and other transitive dependencies also need review.
- The plugin audit reports high-severity issues in Zod and body-parser. The MCP server uses stdio, so the presence of body-parser does not by itself establish an exposed HTTP endpoint.

Fix: update Storybook and its related packages together first, then plan supported Next/Vitest/Vite upgrades and review Zod compatibility. Rebuild the committed plugin bundle after dependency updates. The vulnerable PostCSS copy reported for the web app is nested under Next; updating only the app's top-level PostCSS will not remove it. Add recurring dependency checks and an update cadence. Avoid a blanket forced upgrade without running the conformance and production-build checks.

**5. P2 — Deletions are mishandled in opposite ways locally and in CI. Partly reproduced; CI behavior confirmed from its command.**

Sources: [src/shared/protoFolders.ts:93](/Users/lucas/playground/src/shared/protoFolders.ts:93), [.github/workflows/protos.yml:81](/Users/lucas/playground/.github/workflows/protos.yml:81).

Locally, deployment passes deleted `.tsx` paths to the checker, which tries to read them. The direct gate probe returned `ok: false` with `ENOENT`, preventing an intentional screen removal from being published through `/deploy`. Renames can hit the same issue through their old path.

CI uses `--diff-filter=ACMR` for both laws and flow selection, so a deletion-only PR supplies neither job with affected paths. Deleting a linked screen or flow state can leave surviving navigation broken; a static build need not reject a string-based route or state reference.

Fix: retain deletion/rename metadata to determine affected folders, check surviving screens/flows, and do not read removed files as entries. Add deletion-only and rename-only regression cases, including a surviving link to the deleted screen.

**6. P2 — Deployment cannot resume after a failure following the commit. Reproduced.**

Source: [scripts/deploy.ts:133](/Users/lucas/playground/scripts/deploy.ts:133).

Deployment decides whether there is work entirely from the working tree. Once it commits, a failed push or failed PR creation leaves a clean tree, so rerunning the command returns “Não há nada para publicar” instead of completing publication.

Probe: used an isolated Git repository with a local bare remote and a fake `gh` executable. The first attempt committed and pushed, then returned a simulated PR-creation failure. The second attempt stopped at `changes` with “nothing to publish.” No remote GitHub operations were performed.

Fix: make the stages resumable. Detect unpushed branch commits and a pushed branch with no open PR; skip only the already-completed stages. Revalidate the branch diff against its base when resuming. Cover failures at push, PR creation, and check retrieval.

**7. P2 — One malformed URL terminates the exploration server. Reproduced.**

Source: [scripts/explore-server.mjs:92](/Users/lucas/playground/scripts/explore-server.mjs:92), [scripts/explore-server.mjs:241](/Users/lucas/playground/scripts/explore-server.mjs:241).

The asynchronous request callback has no top-level rejection handler. `decodeURIComponent` throws on malformed encoding; JSON parsing and file reads elsewhere in the callback can also throw. An isolated server receiving `GET /%` exited with code 1 and `URIError: URI malformed`. This is a local availability issue: the server binds to loopback and checks Host/Origin. A crash also loses its in-memory comment queue.

Fix: catch request-handler failures, return a controlled 400/500 response, and keep the server running. Validate JSON file contents and request-body shapes before use. Test that a malformed request is followed by a successful normal request. For writes to `index.html` and state files, consider atomic replacement to protect against interrupted writes.

**8. P2 — Flow loading failures have no recovery state. Confirmed by code inspection.**

Source: [web/app/[designer]/[screen]/FlowPlayer.tsx:53](/Users/lucas/playground/web/app/[designer]/[screen]/FlowPlayer.tsx:53).

The flow import has no rejection handler. State import failures are rethrown for every state except `hidden`, and the resulting promises have no terminal catch. A failed initial import leaves an empty stage; a later failed state can leave the previous state visible indefinitely while the logical trail has advanced. There is no user-visible error or retry control.

Fix: track loading and failure explicitly, handle both import levels, retain the last valid state deliberately, and offer retry/reload. Define how remote input behaves while a requested state is loading. Test rejected imports and a delayed destination receiving additional key presses.

**9. P2 — The documented navigation pattern nests interactive elements. Confirmed by source and documentation.**

Sources: [web/README.md:35](/Users/lucas/playground/web/README.md:35), [scripts/render-harness/next-link.tsx:4](/Users/lucas/playground/scripts/render-harness/next-link.tsx:4).

Wrapping a kit button in `next/link` produces `<a><button>...</button></a>`, explicitly acknowledged in the README. It creates invalid interactive nesting and multiple keyboard targets for one visual action. The current link-render test checks rectangle equivalence, so it does not catch the semantic/accessibility problem.

Fix: add a link-capable variant or composition API that renders one native anchor with the kit's appearance. Preserve button semantics for actions. Add keyboard and accessibility checks that assert a single interactive target and an accessible name.

**10. P2 — Some render tests report “passed” when no browser check ran. Reproduced.**

Source: [tests/checks/corpus.render.test.ts:12](/Users/lucas/playground/tests/checks/corpus.render.test.ts:12).

Returning early from the test after printing “skipped” counts as a pass. Running `CHROMIUM_PATH=/nonexistent ... vitest run tests/checks/corpus.render.test.ts` reported all five tests passed even though every render was skipped. Similar early returns appear in the flow-probe tests. CI installs Chromium, but runtime/browser-launch failures should still be visible rather than converted into success.

Fix: fail on unavailable rendering in CI; use the test runner's explicit skip mechanism only in a deliberate local mode. Make the test summary distinguish executed assertions from unavailable coverage. The normal full-suite run in this audit had Chromium available and passed separately.
